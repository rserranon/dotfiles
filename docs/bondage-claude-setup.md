# Bondage-sandboxed Claude Code

This document describes how Claude Code is launched on this machine. It is not a
generic guide; it describes a specific, working configuration with the rationale
behind each choice. If something in the stack breaks, read this before touching
anything.

## What this is

Claude Code is launched through a three-layer chain instead of run directly:

```
alias claude  →  bondage  →  nono  →  /Users/robert/.local/share/claude/versions/X.Y.Z
```

Each layer does one job:

- **bondage** verifies that the Claude Code binary on disk matches a pinned
  SHA-256 hash, and assembles the exact argv for the layers below. It is the
  trusted launcher.
- **nono** is a kernel-level sandbox (Seatbelt on macOS). It restricts which
  files and network destinations the launched process can touch. Once applied,
  the sandbox cannot be lifted from inside the process — the kernel enforces it.
- **Claude Code** itself runs sandboxed. It can read/write the current project
  directory plus a small allow-list of system paths; it cannot read SSH keys,
  AWS credentials, browser cookies, or shell history.

The point is not paranoia. It is to make the launch decision explicit: this
exact binary, these exact secrets, this exact sandbox profile — every time.

## Why bother

- Coding agents run arbitrary code generated by an LLM. Default trust assumes
  that code only touches what you intend. Bondage + nono make that assumption
  enforceable rather than aspirational.
- Homebrew and native installers auto-update. Without pinning, "the Claude Code
  binary you approved" silently becomes "whatever shipped today." Bondage's
  hash pins make every upgrade a deliberate event.
- macOS Keychain holds the Claude.ai OAuth session. The nono profile explicitly
  allows Keychain access for Claude Code only, so login persists across sessions
  without leaking Keychain access to anything else.

## Installed components

- `bondage` — `brew install nvk/tap/agent-bondage`
- `nono` — `brew install nono`
- `envchain` — `brew install envchain` (installed but not currently used; the
  active config sets `use_envchain = false` because we're on OAuth, not API key)
- `claude-code` profile — pulled from the nono registry:
  `nono pull always-further/claude`, installed at
  `~/.config/nono/packages/always-further/claude/profiles/claude.json`

## Config files

### `~/.config/bondage/bondage.conf`

Bondage's main config. Pins the three helper binaries (`nono`, `envchain`) and
the Claude Code target. Hashes are real SHA-256s; do not edit them by hand.
Use `bondage repin` instead (see Maintenance below).

Key sections:

- `[global]` — paths and hashes for `nono` and `envchain`. Also
  `nono_profile_root`, which points at the directory containing the nono
  profile JSON file. We point this at the registry package directory directly:
  `/Users/robert/.config/nono/packages/always-further/claude/profiles`. This
  means bondage looks for `<root>/<profile_name>.json` — and the file is named
  `claude.json`, so the profile config uses `nono_profile = claude` (not
  `claude-code`, even though `nono profile list` displays it that way).
- `[defaults "agent-nono"]` — shared nono sandbox settings (allow workdir,
  allow `/dev/tty`, etc.).
- `[defaults "claude-target"]` — the pinned Claude Code binary path and hash.
  Bondage's `repin` command auto-canonicalizes symlinks, so this points at
  the resolved version directory under `~/.local/share/claude/versions/X.Y.Z`.
- `[profile "claude"]` — combines the defaults blocks. `use_envchain = false`
  because OAuth doesn't need env-var secret release. `touch_policy = none`
  because we are not using Touch ID gating.

Notable omissions: there is no `touchid` line in `[global]` because we don't
use Touch ID. The example config has it; we removed it.

### `~/dotfiles/aliases/aliases`

Defines the `claude` alias. Currently:

```bash
alias claude='bondage exec claude /Users/robert/.config/bondage/bondage.conf --'
```

**Important: it uses `bondage exec`, not `bondage chain`.** Empirically, `chain`
swallows nono's stderr on macOS and can cause silent exits where Claude Code
fails to start without any visible error. `exec` is the verbose variant; errors
surface and Claude Code starts reliably. Both are documented in the bondage
README; we use `exec` because of the macOS stdio behavior.

The trailing `--` is mandatory — it separates bondage's own args from args to
pass through to Claude Code.

### `~/.zshrc`

Contains:

```bash
export DISABLE_AUTOUPDATER=1
```

This disables Claude Code's background auto-updater. Without it, Claude Code
silently downloads new versions into `~/.local/share/claude/versions/`, breaking
the bondage hash pin until manually repinned. Disabling means upgrades are
deliberate events (see Maintenance).

## Daily use

From any project directory:

```bash
cd ~/development/python/my-project
claude
```

The alias resolves to the bondage chain. Bondage prints a short verification
preamble (verified target, verified nono helper) and exec's the sandboxed
Claude Code session. The current working directory is automatically
read+writable inside the sandbox.

Outside the project directory, sensitive paths are denied by the nono
`claude-code` profile: `~/.ssh`, `~/.aws`, browser data, shell history, shell
configs. Claude Code cannot read or write them. The `bypass_protection` rule
in the profile specifically re-allows `~/Library/Keychains` so the OAuth
session token can be read.

## Maintenance

Bondage fails closed when any pinned binary changes hash. This includes:

- `brew upgrade` of nono, envchain, or anything else pinned globally
- A new Claude Code version landing in `~/.local/share/claude/versions/`
  (only happens manually now that auto-update is disabled, but `claude update`
  or a reinstall triggers it)

When a pin goes stale, `claude` won't launch. The fix loop:

```bash
bondage doctor ~/.config/bondage/bondage.conf
# Read what it says. Doctor prints the exact repin command needed.
bondage repin-globals ~/.config/bondage/bondage.conf   # for nono/envchain drift
bondage repin claude ~/.config/bondage/bondage.conf    # for claude binary drift
bondage doctor ~/.config/bondage/bondage.conf          # should now show: status: clean
```

If `repin claude` needs the new version path (because Claude Code's directory
name changed), update the `target = ...` line in `[defaults "claude-target"]`
to the new version directory first, then repin.

## Updating Claude Code

Auto-update is disabled. To pull a new version:

1. Update Claude Code through whatever its update mechanism is. New versions
   appear as new directories under `~/.local/share/claude/versions/`.
2. Edit `~/.config/bondage/bondage.conf` and update the `target = ...` line
   in `[defaults "claude-target"]` to the new version directory.
3. Run the maintenance loop above to repin and verify.

## Troubleshooting

**`claude` exits immediately with no UI, no error.**
You are probably using `bondage chain` (perhaps because the alias was
reverted). Switch to `bondage exec` in the alias. To debug live, run
`bondage exec claude ~/.config/bondage/bondage.conf` directly — `exec` surfaces
nono's errors where `chain` hides them.

**`nono: Profile read error: profile file not found`.**
The `nono_profile_root` in `[global]` and the `nono_profile` in
`[profile "claude"]` don't combine to a real file path. Check
`ls $nono_profile_root/$nono_profile.json`. If the nono registry has moved
the file, update `nono_profile_root` to match.

**`bondage doctor` says `status: stale`.**
A pinned binary changed. Run the suggested repin command, then doctor again.

**Login prompts on every launch.**
The nono sandbox is blocking Keychain access. The `always-further/claude`
registry profile has a `bypass_protection: $HOME/Library/Keychains` rule that
should prevent this. Verify with `nono profile show claude-code` and look for
that line in the output. If it's missing, the profile was updated and you
need to pull a newer version with `nono pull always-further/claude --force`.

**Bondage works manually but the alias doesn't.**
Check `type claude` to see what the alias actually expands to. It must reference
the correct config path and use `exec`, not `chain`. The alias is defined in
`~/dotfiles/aliases/aliases`.

## Files this setup touches

- `~/.config/bondage/bondage.conf` — bondage config (hash pins, profile refs)
- `~/.config/bondage/bondage.conf.bak` — manual backup before edits
- `~/.config/nono/packages/always-further/claude/` — registry-installed nono
  profile, managed by `nono pull`
- `~/.local/share/claude/versions/X.Y.Z` — Claude Code binaries (one per
  installed version, oldest versions can be deleted to save space)
- `~/dotfiles/aliases/aliases` — the `claude` alias
- `~/.zshrc` — `DISABLE_AUTOUPDATER=1` export

## Things explicitly not done (and why)

- **No Touch ID gating.** `touch_policy = none`. Adds friction to every launch
  for a security benefit that's redundant with the Keychain-backed OAuth flow
  already requiring biometric/password to unlock Keychain.
- **No envchain.** `use_envchain = false`. envchain is for releasing secrets
  from Keychain as environment variables; OAuth uses Keychain directly and
  doesn't need env vars. Would be useful if we switched to API key auth.
- **No tool_root copy pattern.** Bondage's example config suggests copying
  binaries into `~/.bondage/tools/<name>/<version>/` and pinning the copy.
  We pin the native installer's binary directly under
  `~/.local/share/claude/versions/`. Simpler; less indirection. The tradeoff
  is one extra step on update (point at the new version directory).
